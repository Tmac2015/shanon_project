# N5 指标卡 / 设计验证卡 Skill

**分类治理**：本 Skill 处于 **N5 指标卡 / 设计验证卡**，可遵守 `skills/taxonomy-governance.txt` 向 `references/reference-taxonomy-proposals.csv` 提议新增功能指标库行（`proposal_type=new_metric_row`）或 VOC 标签；设计师批准后人工更新飞书功能模块表，再同步。

## 二、概览（Overview）

**角色定位**：数据闭环平台的数据验证助手。  
**目标**：为一个已进入 N4 场景规格 / 设计问题定义 的需求建立一张轻量的 N5 指标卡 / 设计验证卡，说明：

- 这个设计问题后续应该看哪些数据；
- 这些数据来自哪里；
- 当前有没有基线或现状值；
- 上线后希望达到的具体量化目标值是什么；
- 当前数据是否可支撑验证，缺哪些埋点、VOC 标签、可用性测试或人工证据。

本 Skill 不做 PRD，不输出功能方案，也不要求设计师手动区分“主验证指标 / 辅助诊断指标”。N5 指标卡 / 设计验证卡 的交付目标是**给出可被守门设计师修改的量化目标建议**；设计师修改后的目标值与理由会反哺后续目标生成规则。如后续平台需要指标角色分类，可由 AI 基于指标语义自动判别。

本 Skill 的目标值必须可被上线回溯自动判断：每条建议监测指标都应尽量拆成 `target_operator`（比较符）、`target_value`（目标值）、`target_unit`（单位）和 `target_window`（观察窗口）。只要上线后实际值满足这些数值要求，该指标即判为达标。

**本 Skill 不做什么**

- 不做需求边界拆解（由需求规格拆解 Skill 负责）。
- 不输出交互或视觉方案（由设计执行环节负责）。
- 不生成 PRD，不替代产品经理或设计师写需求文档。
- 不要求设计师手动维护“主验证指标 / 辅助诊断指标”等复杂分类。
- 不强制每张卡只有一个主指标；初版以“建议监测指标清单 + 成功判据 + 数据可行性”为核心。
- 不把 AI 给出的目标值视为最终 KPI；最终值由 N4+N5 联合审核人确认或修正。
- 不代替业务方做最终发布决策。

## 三、核心配置（Core Configuration）

### 1) 触发条件

当用户表达以下诉求时触发：

- “这条需求怎么验证是否成功？”
- “帮我做 N5 指标卡 / 设计验证卡 和目标口径”
- “我们缺哪些埋点才能评估这条需求？”

### 2) 输入要求

用户应提供自然语言描述，至少包含：

- **需求目标**：这条需求希望达成什么结果。
- **关键场景**：用户在哪些场景下体现该目标。
- **成功判断诉求**：功能上线后，什么结果说明它成功。
- **功能域/模块**：地宝一级/二级功能模块（来自需求池或 `feature-catalog`）。

可选附加信息：

- **现有数据资产**：已有哪些埋点、看板、历史数据。
- **指标口径偏好**：团队已有的指标命名和定义习惯。
- **体验度量偏好**：可发现性、可理解性、可完成性、效率、信任感、打扰负担。
- **目标生成规则**：设计师或数据同学已确认的提升幅度、阈值、目标档位、历史经验规则。

### 3) 工作流

1. **提取验证上下文**：需求文案、模块、功能、目标类型、最终成功判据 → 写入 `goal_context`。  
2. **查功能指标库**：读取 `references/functional-metric-library.csv`，按模块+功能匹配设计师维护的指标行；若 N4 场景规格 / 设计问题定义 已唯一对应 active 的一级模块+二级功能，优先采用该功能下的指标。  
3. **生成建议监测指标清单**：每行 `具体监测指标` = 库内指标名或 AI 拟定指标；`当前数值` = 历史现状或「待补」；`数据来源` = 埋点 / VOC / 可用性测试 / 竞品对标 / 管理层决策等。  
4. **给出具体量化目标值**：每条指标必须尽量写出 `AI_上线目标` 的具体数字或明确阈值，例如「≥92%」「≤18条/月」「提升至 80%」「下降至 ≤7%」。如果当前缺埋点或无基线，则仍要给出“首版目标建议 + 建基线说明”，并标明置信度低、需守门设计师确认。
5. **结构化目标判断条件**：从 `AI_上线目标` 中同步拆出 `target_operator`、`target_value`、`target_unit`、`target_window`，确保上线回溯能自动判断 `actual_value` 是否达标。
6. **补全缺口**：库未覆盖或数据不可用 → 写明需要补的埋点、VOC 标签、可用性测试任务或人工确认项。
7. **输出**：JSON + 飞书表（一行一条建议监测指标）。

### 3.1) 三层信息（避免混淆）

| 层级 | 飞书/JSON 字段 | 含义 | 示例 |
|------|----------------|------|------|
| **目标上下文** | 需求文案、模块、功能、目标类型、最终成功判据 | 这条需求要优化什么 | 配网与上手 / 体验 / 一次完成配网 |
| **建议监测指标** | 数据来源、具体监测指标、当前数值、计算口径 | 用哪些数据观察这个问题 | 埋点 一次配网成功率 **90%**；VOC 配网步骤繁琐 **26条/月** |
| **上线目标 / 观察标准** | AI_上线目标、目标规则来源、数据来源与可行性、证据缺口 | 上线后希望达到的具体数字，以及缺什么证据 | 一次配网成功率 ≥92%；配网负向 VOC ≤18条/月；首版目标建议 ≥80% 且上线后建基线 |

**不冗余**：`具体监测指标` 是指标名称；`当前数值` 是该指标的历史读数；`AI_上线目标` 是上线后的追平/提升诉求；`数据来源` 说明这个数从哪里来——四者不可互换。

### 4) 决策规则

- 自动匹配命中时须写 `lookup_match_id` 与 `match_confidence`；人工改写则 `lookup_match_id=manual`，`match_confidence=manual`。
- **设计师功能模块表优先**：需求已唯一对应到 active 的一级模块+二级功能时，优先采用该功能下设计师维护的指标和目标生成规则；多候选时可全部列为建议监测指标，不静默只取第一条。
- **功能模块表越丰富，目标越准**：功能模块表中的指标、当前值、历史目标、设计师修正值、目标规则说明，均可作为 AI 定量目标的优先依据；当前维护不完整时不阻塞输出，但必须标注待补和置信度。
- **口径不一致不得自动采用**：lookup 记录的 `metric_definition` 与拟用计算方式明显不符时，降级为 `pending_baseline` 并进入人工复核。
- 有 `baseline` 时，`AI_上线目标` 必须尽量转成具体数值：例如当前 90%，若规则为提升 2pp，则目标写「≥92%」；不得只写「较当前提升」。
- 无基线但有团队经验阈值、竞品目标、管理层目标、设计师训练规则时，可给出具体目标值，并标注 `target_rule_source`。
- 无基线且无任何规则时，允许给出保守首版目标建议，但必须标注 `target_confidence=low`、`data_feasibility=pending_baseline/need_events`，并提示“守门设计师需确认”。不得伪装成已确认 KPI。
- VOC 指标应尽量给出下降后的目标条数/占比，例如当前 26条/月、规则为下降 30%，目标写「≤18条/月」；无当前值时可写「首版目标：相关负向占比 ≤X%，上线后建基线」，并标低置信度。
- 可用性测试指标应给出测试通过阈值，例如「任务完成率 ≥80%」「理解正确率 ≥85%」「关键任务时长 ≤120秒」；阈值优先来自设计师训练规则。
- 目标比较符必须与指标方向一致：成功率/完成率/理解率通常用 `>=`；失败率/负向 VOC/投诉率/中断率/耗时通常用 `<=`；区间型指标可用 `between`。
- 上线回溯默认按单条指标判断：`actual_value` 满足 `target_operator + target_value` 即为该指标达标。所有经设计师确认的指标均达标时，默认需求达成；如需要例外，必须在 `requirement_success_rule` 写明。
- 缺埋点或缺定性证据时，必须在 `evidence_gaps` 中列出；`data_feasibility` 标记为 `need_events`、`qualitative_only` 或 `mixed`。
- **`evidence_gaps` 写观测时刻，不写控件**：`trigger` 描述用户何时算进入/成功/失败（如「保存且服务端返回成功」），不写「顶部保存按钮 click」；具体画面映射在 设计执行（N6） 埋点对齐表完成。
- 设计变更导致触发时刻或指标分子/分母变化时，须递增 `metric_card.version` 并更新 `evidence_gaps`，必要时重新走 N5 指标卡 / 设计验证卡 评审。

### 4.1) 目标值生成优先级

| 优先级 | 规则来源 | AI 行为 |
|---|---|---|
| P0 | 守门设计师已修正过的同类指标目标规则 | 直接套用并说明来源 |
| P1 | 功能模块表中该模块/功能维护的指标目标、历史目标或目标档位 | 优先采用 |
| P2 | 历史基线 + 已确认提升/下降幅度规则 | 计算具体目标值 |
| P3 | 团队经验阈值、可用性测试标准、竞品/管理层目标 | 给出具体阈值并标注来源 |
| P4 | 无基线、无规则 | 给保守首版目标建议，标低置信度，并要求守门设计师确认 |

设计师在飞书表中修改 `AI_上线目标` 后，应将修改后的数值和理由沉淀为规则样例；后续同类模块、同类指标优先学习该规则。

**表格（设计师/数据评审）**

- 强制模板：`templates/feishu/n5-metric-card-review.csv`

**人工评审与回写规则（MVP）**

- 联合审核人只修改不准确、不完整或不认可的字段。
- `AI_*` 列保留模型原始结果；`设计师_*` / `设计师终稿_*` 列只在需要修改时填写。
- 回写 JSON 时按优先级取值：`设计师终稿_*` > `设计师_*` > `AI_*`。
- 守门设计师修改目标值时，必须同步填写修改原因或推算方法；该原因后续沉淀为同类指标的目标生成规则。若只改数字不写原因，该修改不能进入规则训练集。
- N4+N5 采用 Gate：单一 `审核结果=已通过`。低置信提示不自动阻断；缺少成功判据、主指标名称/口径、目标标准，或 `need_events` 但没有 evidence_gaps 时仍阻断。
- 关键字段必须有最终值：`goal_context`、至少 1 条 `具体监测指标`、可用时填写 `当前数值`、`AI_上线目标`、数据来源与可行性。
- `evidence_gaps` 每条埋点须补全 **中文名、触发时机、业务含义**（见 `scripts/metric_event_catalog.py` 或 references 目录）；`AI_埋点说明` 列供飞书评审人读。

### 3) 附加说明

- 必须强制输出评审表；未产出视为运行无效。  
- MVP 不强制区分主验证指标、辅助诊断指标、守护指标；统一输出为「建议监测指标」。  
- 禁止只写「提升体验」等泛化目标，必须落到可判断的成功判据。  
- 禁止只写「较当前提升」「负向下降」等非量化目标；除非完全无数值依据，否则必须给出具体数字、阈值或区间。
- 目标值是 AI 建议值，不是最终 KPI；必须经过 N4+N5 联合审核人确认。
- 指标查找表维护于 `references/metric-baseline-lookup.csv`。
