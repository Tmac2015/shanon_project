# 反馈优化分析技能

**分类治理**：本技能处于 **反馈优化分析（N2a）（入需求池前）**，须遵守 `skills/taxonomy-governance.txt` — 继承反馈标签匹配与路由（N1）的“启用中”分类归档；不得新增正式 VOC 标签或功能模块。

## 二、概览

**角色定位**：资深产品体验分析专家 + UX 研究分析师。  
**目标**：把负面反馈从“抱怨集合”诊断为“真实体验失败模式”，并生成有证据、有根因假设、有用户任务、有重要性建议的优化需求草案。

**本技能不做什么**

- 不做增量机会探索（由增量机会发现技能负责）。
- 不做最终优先级裁定或排期决策（由需求评审与分流技能负责）。
- 不做完整需求规格拆解（由需求规格拆解技能负责）。
- 不定义指标口径（由指标卡定义技能负责）。
- 不输出 UI 方案。

## 三、核心配置

### 1) 触发条件

当用户表达以下诉求时触发：

- “这批评论能归纳成哪些优化问题？”
- “帮我从反馈里生成优化需求草案”
- “某模块最近投诉上升，分析一下”

### 2) 输入要求

用户应提供自然语言描述，至少包含：

- **反馈内容**：与问题相关的用户原话或反馈集合。
- **来源信息**：反馈来自哪里（如应用商店评论、用户净推荐值调研、客服工单）。
- **基础上下文**：至少说明问题大致发生在哪个功能或流程。
- **反馈标签匹配与路由（N1） 标签结果**：优先使用已通过评审的 `reviewed_tags`、`matched_feature_modules`、`pain_domain`、`route_decision`；若只有源标签或低置信 AI 标签，需在置信度中体现。

可选附加信息：

- **现有需求池信息**：用于防重和合并判断。
- **功能映射信息**：页面/模块映射，便于定位问题归属。
- **源标签统计**：VOC 平台三层标签分布、标签词典版本、无标签/AI 补标比例。

### 3) 工作流

1. **清洗与证据准备**：读取 N1 已过滤、按需拆分、路由、去重并人工通过的软件问题单元，保留父反馈、完整原文、问题证据片段、源标签、终稿标签、功能模块、产品型号、版本和时间窗。不得按整条评论的正面、负面或混合情感再次过滤。  
2. **LLM 功能归属（正式必跑）**：在生成任何问题簇前，把全部 N1 可分析代表反馈、原文证据和正式功能目录交给 LLM 智能体。每条反馈必须先选择一个且仅一个正式功能域与主功能模块；无法可靠归属唯一功能的反馈进入功能待确认池，不得参与成案。N1 的标签和粗粒度功能映射只能作为线索。  
3. **功能内主题发现**：只能在同一个主功能模块内部，按“用户可观察失败＋用户任务＋失败环节＋所需调查或解决路径”形成候选问题簇。不同功能不得因为都属于“看不懂”“找不到”“不稳定”等抽象体验而合并。规则、标签、关键词和预设失败模式不能先生成草案再交给 LLM 审核。  
4. **主题精炼与证据分配**：基于主题分析与扎根理论，从用户原话中提炼痛点主题，合并同义表达，拆分混杂主题。每条输入证据在功能归属层必须且只能出现一次；在对应功能桶内也必须且只能进入一个独立问题簇或未聚类集合。缺失、重复归属或生成不存在的证据时，整次运行失败。  
5. **原始需求归纳**：每个独立问题簇必须先产出一条正向、单一的原始需求。根据实际证据自然归纳，允许任务句、目标句或结果句，不强制使用“用户需要……能够……”等统一模板；应保留场景与目标，不得只复述崩溃、卡顿、找不到或看不懂等痛点，也不得提前指定按钮、页面布局或技术实现。  
6. **体验问题诊断**：使用用户旅程图定位失败环节，使用五问法提炼根因假设，使用待办任务法识别用户真实任务。  
7. **需求草案转化**：仅对 LLM 已完成功能归属和语义精炼的独立问题簇，用“我们可以怎样”的句式将痛点转成设计机会表达；功能待确认池、标签兜底池和混杂主题不得生成需求草案。  
8. **重要性建议**：结合严重度×频率矩阵、卡诺模型和需求优先级评估思路，输出重要性建议和依据；该建议只供需求评审与分流（N3）参考，不替代最终优先级裁定。  
9. **输出**：一份机器可读的 JSON 文件＋一张合并飞书评审表。

### 4) 决策规则

- 默认成案门槛：>=8 个不同父 VOC 支持的同类软件问题（可按产品线配置调整），但不得只按数量成案；同一父 VOC 的多个子问题不得在同一问题簇内重复计数。
- 低频高危：5-7 条可成案，但必须说明严重度、主路径影响和置信度。
- 禁止泛化：不得使用“提升体验”替代具体失败描述。
- 禁止八股句式：同一批次不得大面积重复“用户需要”“用户希望”“能够”等固定开头；句式变化不得改变含义或扩大证据边界。
- 纯硬件问题默认不生成 App 优化草案。
- 重要性建议不得写成最终排期；本技能只输出 `importance_suggestion`（重要性建议）和 `importance_reason`（重要性依据），最终推进、暂缓或合并由需求评审与分流技能裁定。
- 需求草案必须停留在“问题诊断＋机会表达”层级，不输出完整场景列表、范围内外、主流程步骤、验收标准或指标口径。
- 标签使用规则：
  - `reviewed_tags` 是聚类强线索，但不能单独作为成案依据。
  - `source_tags` 仅作为证据口径和回溯字段，不直接等同于平台最终标签。
  - 正式 `feature_domain` / `primary_feature_module` 是 N2a 的一级成案边界；只有相同主功能模块内的反馈才可继续聚类。功能归属仍不能直接生成 `pain_theme` 或 `logic_pain_point`。
  - N1 的 `matched_feature_modules` 只是粗粒度线索，不等于正式功能归属，必须对照启用中的功能目录重新判断。
  - `ai_predicted_tags` 若未人工确认，只能辅助分析；低置信补标不得计入高置信成案门槛。
- 同一三级标签下若出现多个失败模式，必须拆成多个主题簇。
  - 不同标签路径只有在“正式主功能模块相同、用户失败环节相同、解决路径相同”时才可合并，并保留全部 `source_tag_paths`。
  - 若认为 **VOC 标签或功能分类与原文/失败模式不匹配**，在草案 `tag_evidence_note` 或主题簇 `备注` 中说明，供设计师审核；**不得**为迁就标签而改写问题诊断。
- 正式执行顺序必须是 `完整证据＋正式功能目录 → LLM 唯一功能归属 → 各功能内部语义聚类/问题诊断 → 两层唯一证据归属校验 → 子簇门槛计算 → 需求草案`；仅让 LLM 对规则草案做事后字段审核，视为无效 N2a 运行。
- 拆分后的独立子簇必须重新计算门槛；父标签池总数不得沿用。
- 置信度必须分维度判断：证据可信度、语义聚合可信度、功能归属可信度、成案就绪度。不得用负面关键词命中率代替语义一致性，也不得因功能模块待确认而否定问题簇本身。
- LLM 对每个问题簇必须说明语义聚合强度、边界争议，以及是否存在需要拆分的潜在子问题；规则引擎只能校验和呈现，不能用关键词覆盖该判断。
- 只有证据缺失/虚构/重复归属、语义明显混杂且应拆分、或缺乏可追溯原话时，才将问题簇判为阻断；功能归属待确认属于分类复核项。
- 用户主界面使用一张扁平需求表，一行对应一条原始需求；主列为“原始需求、功能模块、证据、置信度、需求依据、AI 建议、人工决定”。其中置信度只表示需求提炼是否准确，不混入评论数量、成案门槛或功能归属；用户直接通过相关评论数量判断证据多少。痛点、失败环节、根因假设和字段级合规检查折叠到分析与审计信息。
- 功能模块作为表格列展示，不再使用多层功能卡片和问题簇卡片；功能待确认反馈单独展示且不能成案。当前版本不生成跨功能洞察模块。
- 完成后停在 N2a，未经单独人工批准不得自动进入 N3。

### 5) 方法论引用

本技能应显式使用成熟方法论作为分析内核：

| 方法论 | 在本技能中的用途 |
|---|---|
| 主题分析 | 从大量反馈中识别反复出现的主题与模式 |
| 扎根理论 | 从用户原话中逐层提炼核心问题，避免直接跳到需求 |
| 用户旅程图 | 定位问题发生在哪个体验阶段 |
| 五问法 | 从表层抱怨追问到根因假设 |
| 待办任务法 | 识别用户真实任务，而不是停留在功能表面 |
| “我们可以怎样”问句 | 将痛点转成可讨论的设计机会表达 |
| 卡诺模型 | 判断体验价值类型：基础型、期望型、兴奋型 |
| 用户体验结果框架 | 说明该问题主要影响哪类体验结果 |
| 需求优先级评估法 | 形成重要性建议：影响面、影响强度、证据可信度、粗略可行动性 |

**表格（设计师评审）**

- 强制模板：`templates/feishu/n2a-optimization-review.csv`
- 表格组织方式：一行对应一个独立原始需求。主视图只展示原始需求、功能模块、证据、置信度、需求依据、AI 建议和人工决定；置信度只表示需求提炼可信度，痛点主题、逻辑痛点、用户任务、失败环节、根因假设等保留在同一行的折叠分析与审计信息中。
- 这样做的原因：设计师评审时通常是围绕“这条草案是否成立”做判断，把批次、主题和草案拆成三张表会增加来回对照成本；合成一张表更适合人工通读和修改。

**人工评审与回写规则（最小可用版本）**

- 设计师不需要逐字段填写或逐项确认；只修改不准确、不完整或不认可的字段。
- `AI_*` 列保留模型原始结果，不建议覆盖；`设计师_*` / `设计师终稿_*` 列只在需要修改时填写。
- 回写 JSON 时按优先级取值：`设计师终稿_*` > `设计师_*` > `AI_*`。
- 每条优化草案只需要做一次行级确认：`设计师确认=已通过` 且 `是否批准入库=是` 才允许进入需求池。
- 关键字段仍必须有最终值：标题、痛点主题、逻辑痛点、用户任务、失败环节、根因假设、证据条数、App 可行动性、重要性建议、**功能域、主功能模块、分类依据**、是否批准入库；若为空，即使已通过也应阻断入库。

**飞书列与 JSON 字段对照**

| JSON | 飞书列 |
|------|--------|
| `original_requirement` | `AI_原始需求` |
| `requirement_confidence` | `AI_需求提炼置信度` |
| `feature_domain` | `AI_功能域` |
| `primary_feature_module` | `AI_主功能模块` |
| `related_feature_modules[]` | `AI_关联功能模块(用|分隔)` |
| `classification_source` | `AI_分类来源` |
| `classification_confidence` | `AI_分类置信度` |
| `classification_reason` | `AI_分类依据` |
| `tag_evidence_note` | `AI_标签证据说明` |
| `classification_mismatch_note` | `备注` |

**与后续技能的边界**

- 本技能输出“重要性建议”，不输出最终优先级分、排期建议或推进裁定；这些由需求评审与分流技能完成。
- 本技能输出“用户任务、失败环节、根因假设和设计机会问句”，不输出完整场景列表、范围边界、主流程步骤或验收标准；这些由需求规格拆解技能完成。
- 本技能可以说明该问题影响哪些用户体验结果，但不定义指标口径；N5 指标卡与设计验证卡技能负责最终成功判据、建议监测指标和数据可行性。
