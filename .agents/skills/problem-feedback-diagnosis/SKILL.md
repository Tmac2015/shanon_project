# 问题反馈诊断

面向炮火和问题管理平台的单条或零散 App 问题，例如某语言文案未翻译、按钮难以点按或状态显示异常；这不是 VOC 批量聚类，也不代替研发根因结论。

保存原话与来源，区分观察事实、可能原因与未知项。从原文可见的入口、控件、操作和预期结果还原用户要完成的任务；缺少真实 App 操作路径时，将任务明确标成基于现有证据的推断，不编造页面路径。截图只有在本次确实可读取时才作为视觉证据；只有附件名称或链接时，不得声称看过截图。

对每个可独立解决的问题，直接生成一条粗需求：说明当前问题、受影响的用户任务、期望改善的结果与边界，不提前指定未经验证的技术方案。逐条保留逐字原文引用与待补证据。按输入提供的当前产品线功能目录，**只选一个最接近的现有模块**，给出模块 ID、所属域 ID、定位理由和 0–1 置信度；优先问题发生的功能/操作，不以横向质量属性（翻译、易用性）代替具体功能。即使证据不完整也要推荐一个最接近的模块，并指出推断依据和缺口；不要输出“功能待确认”、多个并列模块或自造模块。目录不覆盖该产品线时停止定位，不能假装完成。

对故障链路，只在原文支持时分析 App 发起、通信/服务、设备执行、状态回传或 App 展示等失败环节；不要把待验证原因当根因，也不要把设备端问题硬归 App。禁止捏造复现频次、负责人、已确认修复方案或已读取的日志。每条有可引用原文的问题至少形成一条粗需求。

最终产物直接给出事实、最接近的功能归属、用户任务、粗需求、定位依据和置信度。已由输入或后续补充澄清的信息直接纳入结论；剩余证据缺口以陈述句列出，不用反问、请求补充信息或“请人工守门”之类的收尾。若输出结构要求 `next_step`，写成客观的验证或流转动作，而非对用户的提问。人工是否接受、改派或驳回属于产物之后的平台流程，不改变本次分析必须交付完整结论。
