# N2a 反馈优化分析

执行前必须完整阅读项目规范：
`../../../data-closed-loop-platform/skills/feedback-optimization-analysis-skill.txt`。

## 必须遵守的执行顺序

1. 把所有已通过且可进入 N2a 的 N1 软件问题单元和正式功能目录交给正式 LLM 智能体，不得按整条评论的正面、负面或混合情感再次过滤。输入必须包含问题单元 ID、父反馈 ID、问题证据片段、完整原文、源标签、复核后标签、N1 功能线索、来源和重复组频次。
2. 在任何聚类和需求草案产生前，先为每条反馈选择一个且仅一个正式功能域与主功能模块。无法可靠归属唯一功能的反馈必须进入“功能待确认池”，不得参与成案。
3. 只允许在同一个主功能模块内部发现问题簇。必须按“用户可观察失败＋用户任务＋失败环节＋所需调查或解决路径”聚类；不同功能不得因为具有相似的抽象体验而合并成同一需求。
4. 每个独立问题簇必须归纳一条“原始需求”。根据证据自然写清使用场景或任务环节，以及要完成、确认、理解或恢复的目标；允许任务句、目标句或结果句，不强制使用“用户需要……能够……”等统一模板。不得只把痛点换一种说法，也不得提前指定界面或技术方案。
5. 强制检查两层证据唯一归属：每个问题单元 ID 在功能归属层只能出现一次；在对应功能桶内也只能进入一个问题簇或未聚类集合。出现缺失、重复或虚构 ID 时，整次运行失败。簇内证据数量按不同父反馈 ID 计算，不能因一条评论被拆分而虚增门槛。
6. 只能从智能体确认的功能内独立问题簇生成需求草案。每个“主功能模块＋具体失败模式”子簇都要重新计算成案门槛，不得沿用父标签池或跨功能集合的总数。
7. 分开判断证据可信度、语义聚合可信度、功能归属可信度和成案就绪度。功能归属是成案边界，但不得用功能分类结果代替语义一致性判断，也不得把多个维度压成一个含义不清的总标签。
8. 当前版本不生成或展示跨功能洞察。
9. 完成后必须停在 N2a 等待人工确认，不得自动进入 N3。

## 规则引擎的边界

确定性规则引擎可以负责输入规范化、数据结构校验、正式分类映射和门槛计算，但不得根据标签名、固定模板或正则表达式直接产生可发布问题簇。

可以增加第二轮草案审核，但它只能作为折叠的审计证据，不能代替前置语义发现。

## 面向人工评审的输出

主视图必须是一张扁平需求表，一行对应一个独立原始需求。主列固定为：原始需求、功能模块、证据、置信度、需求依据、AI 建议、人工决定。不得用痛点或主题名称替代原始需求。

主表中的“置信度”只表示需求提炼可信度，即原始需求是否准确概括了簇内相关评论。证据强度不单独评级，用户直接通过相关评论数量判断；不得把成案门槛或评论数量混入需求提炼置信度。

原始需求文案应简洁、自然、适合产品人员快速浏览。同一批次不得大面积重复“用户需要”“用户希望”“能够”等模板开头；不得为了句式变化而改变需求含义或扩大证据边界。

功能模块作为表格列展示，不再用多层功能卡片和问题簇卡片组织主视图。功能待确认反馈单独显示为不可成案的待处理池。

主视图不得展示原始结构字段名或逐字段合规报告。证据、功能归属和成案就绪等详细判断只放入折叠审计信息。

痛点、失败环节、根因假设、代表性原话、模型、响应 ID、检查点、数据结构校验和详细验证信息统一放入折叠的分析与审计区。

## 失败关闭与审计保护

出现以下任一情况时，必须停止运行，不得静默退化为纯规则处理：

- 缺少正式 LLM 配置。
- 实际模型与当前正式配置不一致。
- 证据覆盖不完整或归属不唯一。
- 问题主题仍是笼统的标签改写。
- 结构化输出无效。

必须保留原始证据、批次关系、模型响应和新旧版本关系；不得虚构 VOC 证据，不得覆盖历史 N2a 产物。
