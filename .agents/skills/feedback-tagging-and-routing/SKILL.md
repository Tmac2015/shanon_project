# N1 反馈标签校验与路由

本流程必须调用正式 LLM 智能体。纯规则执行只能用于零风险预处理，不得当作正式 N1 初筛或最终结果。

## 必须遵守的流程

1. 保留原始反馈、源标签和稳定 ID。
2. 执行零风险规则预处理，且只能移除空文本、已知平台占位文本和完全重复记录。对完全重复记录记录 `duplicate_of`。VOC API 拉取后的 N1 入口允许使用 active 飞书 VOC 一/二/三级完整路径白名单：命中路径进入主分析；未命中但一级标签为 `APP`、`地图`、`维护` 进入 `tag_prefilter_hold` 待确认；其余未命中记录标记 `filtered_out`，原因固定为 `source_tag_not_in_feishu_voc_whitelist`。原始记录和稳定 ID 必须保留在审计产物中，闸门不得依据情感、星级、关键词或近义判断。
3. 对通过白名单闸门或进入待确认队列的评论调用正式 LLM 做轻量初筛。初筛只判断是否存在可行动问题，以及是否可明确提前过滤；输出保持精简并可审计。
4. 仅当评论明确属于泛泛好评、没有可行动问题，或只涉及客服、物流、安装服务、营销活动时，初筛才可提前路由到 `filtered_out`。正面但含问题、纯硬件、纯软件、软硬件混合和责任不明的评论全部进入深分析。
5. 仅对深分析候选执行完整问题单元拆分、软硬件路由、标签校验、模块映射和语义近义去重。只有存在两个及以上独立可行动问题时才拆分；单问题评论沿用原反馈 ID，子问题使用稳定子 ID，并保留父反馈 ID、完整原文和证据片段。
6. 深分析后，每个问题单元必须且只能路由到 `app_pipeline`、`hold_hardware_pool` 或 `manual_review`；若深分析证实没有可行动问题，才可改为 `filtered_out`。每个语义重复组只保留一个代表问题单元，同时保留出现次数、成员 ID、父反馈 ID、来源和时间跨度。
7. 缺失源标签只降低标签可信度，不得单独触发人工复核；只有标签冲突会实质影响软件归属或问题判断时，才进入人工复核。
8. 返回符合配置数据结构的 JSON，不得只返回自然语言说明。

## 按需拆分规则

只有存在两个及以上独立可行动问题时才拆分。模块不同是强信号，但不是唯一条件；用户任务、失败环节、软硬件路由或调查路径不同也应拆分。同一因果链、同一任务的现象与结果、重试过程、频率和严重度描述不得拆开。

正面背景不得生成问题单元。“设备清洁很好，但地图保存失败”只保留一个地图问题单元；“地图保存失败且预约任务不执行”拆为两个软件问题单元；“禁区已保存但设备仍越界”保留为一个应用到设备执行问题。

拆分后的每个证据片段必须能在完整原文中逐字定位，不得改写为原文中不存在的事实。拆分不覆盖父评论；父评论与子问题必须可双向追溯。

## 根问题合并规则

一个问题单元对应一个重复组，不得按字面变体分组。当问题单元指向同一受影响能力和同一用户可观察失败时，即使使用场景、频率、重试动作、严重度表达或对象不同，也应归为一组。

当失败环节或所需调查路径不同时，必须分组。例如，“无法创建区域”、“区域保存后消失”和“已显示的保存区域未被设备执行”是不同问题。反之，间歇性失败、越过宠物碗禁区、多次发生和重启应用无改善，如果禁区仍然可见，都应归入“已保存禁区未被执行”。

`normalized_text`（规范化问题文本）必须是简短的根问题句子。同一重复组的所有成员必须使用完全相同的 `normalized_text`，并排除频率、重试、客套语、样本编号和偶发对象。

每个重复组必须选择一个现有反馈 ID 作为 `representative_id`（代表记录 ID），并用简短、有证据的理由说明合并根据。出现次数只作为频率证据，不得虚增独立表达数。

## 路由规则

- 先判断原文是否包含明确、可行动的问题、异常、未满足需求或改进诉求。除需要保留到硬件分析池的明确纯硬件体验外，纯正面评价、泛泛好评和没有问题或诉求的信息，路由到 `filtered_out`，过滤原因为 `positive_no_issue`。
- 仅涉及客服态度、物流、安装服务、营销活动等范围外内容，路由到 `filtered_out`，过滤原因为 `out_of_scope_service_logistics_installation_marketing`。
- 正面情感不是自动过滤条件；只要原文同时包含明确问题、故障或改进诉求，仍须继续判断软硬件归属。
- 先将 `experience_scope`（体验范围）分为 `app_interaction`（应用交互）、`app_to_device_execution`（应用到设备执行）、`device_hardware`（设备硬件）或 `ambiguous`（责任不明）。
- 应用交互：问题发生在用户查看、理解、配置或操作应用本身时。
- 应用到设备执行：应用已接受或显示配置，但设备、固件或云端未正确执行。这不是纯应用交互投诉，但属于软件闭环。
- 设备硬件：纯物理、机械、耗材或电气故障，应用端没有有效的控制或可观测介入点。
- 证据充足时，应用交互和应用到设备执行都路由到 `app_pipeline`。
- 纯物理、机械、耗材或设备故障，且应用端无有效介入点时，路由到 `hold_hardware_pool`。
- 只有原文包含负面或异常信号、可能与软件有关，但责任归属或关键证据不清时，才路由到 `manual_review`。
- 源标签缺失、功能模块未命中或标签置信度低，不得单独成为 `manual_review` 的理由；这些问题作为标签质量审计信息保留。
- 明确的硬件故障直接进入硬件池，不进入人工复核；纯硬件正面体验也进入硬件分析池，不进入软件闭环或人工复核。

不得仅根据源标签推断范围。“APP 体验”等粗粒度源标签只是待校验证据，不是结论。必须说明具体的 `software_leverage`（软件介入点），例如配置正确性、状态同步、执行确认、失败解释、恢复路径或无介入点。

## 结果约束

- `filtered_out`：`has_actionable_problem=false`、`needs_manual_review=false`、`software_leverage=none`，且必须给出非 `none` 的 `filter_reason`。
- `app_pipeline`、`hold_hardware_pool`、`manual_review`：`has_actionable_problem=true`，且 `filter_reason=none`。
- `manual_review`：`needs_manual_review=true`；其余三种路由必须为 `false`。
- 每个问题单元必须且只能出现一次，不得生成输入中不存在的证据。一个父 VOC 可以支持不同独立问题，但同一问题簇的频次必须按不同父 VOC 计数，不能用拆分数量虚增用户证据。

## 正式运行契约

正式 N1 输出必须包含 `agent_run`（智能体运行记录），其中 `execution_mode` 必须为 `llm_agent`，并记录轻量初筛与深分析各次调用的非空 provider response ID、模型、技能文件 SHA-256、开始时间、结束时间和每个输入项的已校验决策。零风险预处理的删除项也必须保留原因和追溯关系。任一正式 LLM 调用缺少审计信息时，必须停止批次并报告失败，不得静默退化为规则处理。

## 产物

- `N1/n1-output.json`：保留的代表记录、重复组和智能体审计记录。
- `N1/n1-feedback-review.csv`：包含过滤、按需拆分、路由和去重后的代表问题单元，并带有父反馈与重复组证据列。
- `N1/n1-duplicate-groups.csv`：每个重复组及其成员。
- `analysis/`：下游可使用的应用端代表反馈和人工复核队列。
